# 项目理解与 Rust 重写

## 原有行为

Java `PicTransmitter` 使用 Swing 和全局静态状态，拖拽文件或读取剪贴板后由 `SendThread` 将数据分片。`drawBytes` 把每字节高低四位依次画到两个格子，剩余区域为红色结束标记。`PicReceiver` 使用 AWT Robot 截屏，由 `ImgUtil` 找棋盘格并解析，再交给线程池校验、存入帧号到字节数据的 Map，最后按序合并。

校准画面按 `(row + column) % 2` 黑白交替，左上角黑色。无水印编码为 `nibble * 16 + 8` 的灰度，解码逐像素取灰度平均后除以 16。水印模式中 bit3、bit2、bit1、bit0 分别控制左上、右上、左下、右下子格，1 为黑、0 为白。像素 `R > 200 && G < 50 && B < 50` 表示结束。

## 线上字节格式

所有整数使用大端序，类型标记为 ASCII。

| 帧 | 内容 |
| --- | --- |
| 文件信息 | `f` + 总数据帧数 u32 + Java URLEncoder 编码的 UTF-8 文件名 |
| 文本信息 | `t` + 总数据帧数 u32 + 空名称 |
| 数据 | 帧号 u24（从 1 开始）+ 载荷 MD5 最后两个字节 + 载荷 |

文件名遵循 Java form URL encoding：空格为 `+`，UTF-8 字节使用 `%HH`，安全字符为字母数字与 `.-*_`。信息帧没有校验字段。实际数据头为 5 字节，Java 计算载荷时预留 6 字节，因此 Rust 保留相同计算方式，最后 1 字节空间用于红色结束标记。协议库基础配置 1440×800、4 像素格子下为 72000 格、36000 字节容量和 35994 字节载荷；2.0.8 桌面发送画面采用动态行列数，每帧载荷为 `列数 × 行数 ÷ 2 − 6` 字节。线上字节字段不变，分片容量由校准画面决定。

保留 Java 接收端帧号上限 986894，避免把初始棋盘格的 `0F0F0F` 误作数据帧。空文件的信息帧声明零帧，Rust 可以直接恢复空文件。

## Rust 模块

| 文件 | 职责 |
| --- | --- |
| `src/config.rs` | 内置默认参数、30 / 50 / 100 毫秒间隔选项、灰度/水印模式及几何参数校验 |
| `src/grid.rs` | 棋盘格、灰度/水印编码与逐像素解码 |
| `src/protocol.rs` | 信息/数据帧、MD5、UTF-8 名称、数据切片与补发输入 |
| `src/locator.rs` | 按连续黑白像素运行长度推断完整棋盘格位置与整数格子尺寸 |
| `src/receive.rs` | 单次接收状态、去重、缺失帧、容量限制、按序保存/文本恢复 |
| `src/sender.rs` | egui 原生界面、后台准备、显示时序、停止重置、文件选择与设置页 |
| `src/receiver_ui.rs` | 40% 工作区宽度客户端、靠右启动位置、连续接收控制、主界面水印开关、滚动历史列表、目录与主题设置 |
| `src/receiver.rs` | xcap 多屏扫描、全屏定位、区域截图与裁剪、接收循环和结果输出 |
| `src/transfer_speed.rs` | 常量空间的近期有效载荷速度统计与统一速度格式 |
| `src/windows_capture.rs` | Windows 原生区域截屏、GDI 资源与像素缓冲区复用 |
| `src/bin/` | 两个程序的命令行入口 |

`desktop` 为默认 feature。禁用它时，协议、图像、定位和接收状态均可作为库运行和测试，不引入窗口、剪贴板及屏幕 API。

## 行为修正

客户端不读取配置文件。协议库保留内置的 1440×800 基础画面和 4 像素基础格子，默认数据帧间隔为 50 毫秒；2.0.8 桌面发送端根据窗口可用空间建立动态行列数的画面。发送端设置提供 30 / 50 / 100 毫秒选项，发送或准备文件期间禁止修改。水印默认开启，两端主界面的滑动开关可以切换水印编码，接收端水印开关位于开始接收与停止接收之间；传输期间不能更改编码。发送端直接建立格子，不需要截取自己的屏幕才能初始化。GUI 只由主线程修改，一次仅存在一个发送任务；文件读取在后台完成，停止或重置后准备结果无法启动过期任务。补发复用最初的数据，文件后续变化不会影响分片。

发送端窗口位于工作区左侧，外部尺寸目标为工作区宽度的 60%、高度的 80%；接收端位于右侧，目标为 40% 宽、80% 高，历史列表独立滚动，空间不足时缩小控件。Windows 通过当前窗口的 `MonitorFromWindow` 和 `GetMonitorInfoW.rcWork` 获取所在屏幕工作区，扣除任务栏、原生边框及留白，保留多屏坐标原点。传输格子边长固定为 2 物理像素，行列数均为 4 的倍数，至少 160×80 个格子，画面长宽比限制在 1.2～3.2。窗口可用空间越大，格子数量及每帧载荷越大；准备发送时按当前容量切片。接收端从完整校准棋盘格推断行列数，2.0.7 及更早接收端不支持动态容量画面的自动定位，须同时更新两端为 2.0.8。

显示图片使用最近邻采样，格子边缘与渲染起点对齐物理像素。水印四象限各占一个像素。倒计时从后续原生绘制帧开始，慢帧不会跳过待发数据帧。正在发送时画面尺寸或位置变化会重新展示校准画面，并按新画面容量从第一帧完整重发；同一容量的重复信息帧与数据帧不会丢弃接收端已有的同一文件分片。视口不足以显示完整画面或最小化时暂停，并重新计时当前帧。

正常数据帧使用设置所选的目标间隔，不再按画面尺寸强制延长至 100 毫秒。30 毫秒速度更快，但接收设备处理不足时更容易丢帧；50 毫秒为默认值，兼顾速度与稳定性；100 毫秒适合性能较弱设备或出现丢帧时使用。实际展示速度受屏幕刷新、截图与解析耗时影响，慢帧只会延长停留，不会跳过数据帧。校准与信息帧仍至少展示 1 秒，补发仍至少 200 毫秒。间隔选择仅作用于本次运行，重新启动恢复 50 毫秒。数据头、校验与水印编码保持原有格式。

2.0.9 在两端主界面展示当前传输速度，使用最近约 1 秒的数据载荷统计。2.0.10 将等待提示、传输状态及文件名固定在行左侧，速度固定在行右侧，长文本截断以避免相互挤占。发送端仅在数据帧完成展示后计数，补发数据计入实际发送量；接收端使用现有接收会话缓存的唯一字节计数，附加采样时间到现有进度事件，重复帧不增加速度。统计不改变协议、截图次数、帧展示时序或等待周期，也不为统计复制载荷；等待、停止、暂停和重新校准时清零。接收端进度条加粗为 20 逻辑像素，等待时隐藏蓝色填充，传输中显示进度。

自动定位验证整个校准棋盘格，保留第一/最后行列，可处理屏幕边缘、其他条纹干扰和整数像素格子。2.0.8 根据棋盘格边界确定动态行列数，并检查最低格子数量、行列倍数和画面长宽比。原 Java 的定位基于内部颜色跳变，可能裁掉边缘格子；Rust 不沿用该错误。因此互通测试证明的是字节协议和图像编码，而非旧定位器或新动态容量画面的自动定位兼容性。

接收状态在单线程内顺序更新，完整后才保存，避免原线程池共享总帧数与完成状态的竞态。重复信息帧保留已收到分片。没有信息帧的数据暂时忽略，补发时重新发送信息帧。即使收到不足 10 帧也会在 3 秒无新进度后报告缺失帧。

接收文件名必须为单个路径分量，限制总大小和帧范围，拒绝截断分片。通过目标目录内临时文件写入并原子发布，默认不覆盖已有文件；空文件和无效 UTF-8 都有明确处理。

Windows 接收端首次通过全屏截图定位棋盘格，定位和区域截屏均使用物理坐标，包括未初始化窗口的 CLI 模式。支持现代 DPI 接口的系统使用线程 DPI 作用域；Windows 7 使用进程 DPI 感知降级。定位后只截取传输区域。原生 GDI 路径复用屏幕 DC、内存 DC、top-down DIB 和 RGB 缓冲区，避免每帧复制与转换整个 4K 屏幕。桌面客户端在区域截屏失败时重新定位，不解析缓冲区中的旧画面；CLI 返回截屏错误。macOS、Linux 继续全屏截图，在 RGBA 图像上先裁剪传输区域，再仅将该区域转换为 RGB。GUI 与 CLI 的轮询等待都会扣除本轮截图和解析耗时，超过周期时不再额外等待。

接收端在观察到校准棋盘格时同步确认完整边界，持续校准期间每 500 毫秒复核；确认结果可延续到后续信息帧，避免在信息帧上搜索校准图像。完整边界发生变化时重新建立截图区域与接收容量，确认失败时清除旧区域并重新搜索，禁止按旧容量接收数据。正常数据帧继续只截取已定位区域。

macOS 截屏可能在无权限时返回仅有壁纸的图像，因此接收前显式检测屏幕录制权限。所有定位和裁剪均使用截图物理像素坐标，避免混用逻辑坐标。


## Windows 通用兼容构建

2.0.6 普通 Windows 构建中的标准库与依赖会静态导入 Windows 7 缺少的接口，包括 `bcryptprimitives.dll!ProcessPrng`、`WaitOnAddress` / `WakeByAddress*`、`combase.dll!CoTaskMemFree`，接收端还使用 `SetThreadDpiAwarenessContext`。这些缺失导入可能使双击 exe 时直接装载失败，尚未进入应用初始化或显示窗口。

自 2.0.13 起，Windows 7 SP1 / Windows 10 / Windows 11 共用 `windows-x64` 包，LanSender 和 LanReceiver 继续作为两个独立的桌面程序。默认打包使用自 2.0.7 起采用的 `x86_64-win7-windows-msvc` 目标，从与编译器匹配的 Rust 标准库源码执行 `build-std`。目标的 `target_vendor = "win7"` 使标准库及 `getrandom` 选择旧系统可用的随机数和同步接口。现代 DPI 接口通过 `GetProcAddress` 检测后调用；Win7 GUI 由 winit 已有的 `SetProcessDPIAware` 路径降级，CLI 同样启用进程 DPI 感知。现代系统仍可使用动态检测到的 DPI 功能。

文件对话框依赖采用保留许可证的本地 rfd 源码。对话框与 `src/desktop_paths.rs` 中默认桌面路径处理使用的 `CoTaskMemFree` 均以 `#[link(name = "ole32", kind = "raw-dylib")]` 直接导入 Win7 可用的 `ole32.dll`，防止链接时选择 windows-sys 中指向 `combase.dll` 的同名绑定。Rust 会为该库名自动补上 `.dll` 扩展。项目继续使用 Rust 2024 edition、最低 Rust 1.88 和现有 GUI 依赖；无需降低源码版本。`scripts/package-windows.sh` 生成包含两个 exe 的通用包，旧 `--win7` 参数保留为同一构建的别名；标准库源码可由匹配版本的 `rust-src` 或 `LANBRIDGE_RUST_SRC` 指定的 `library` 目录提供。本次环境绑定 Rust 1.98.1，下载源码按 SHA-256 校验并保存在 `target/build-tools`。

通用包使用静态 CRT，打包完成后自动按 Windows 7 基线检查普通与 delay 导入表、PE 版本及包内容，防止以后重新引入新系统专属的必需接口。仍需要支持程序所需现代 OpenGL 的显卡驱动，Windows 7 系统自带 OpenGL 1.1 不足。静态导入检查只能排除装载阶段的已知问题；Windows 7 / 10 / 11 实机启动、显卡初始化、文件对话框与完整收发仍需验证。

## 保留的协议限制

原协议没有传输 ID、整体文件长度或整体校验，MD5 仅取两字节且只覆盖每帧载荷。接收端不能区分名称、类型和总帧数完全相同的新传输与补发；一次接收未完成时应继续补发原数据，若要换数据须先停止再开始接收。桌面客户端完成一份文件后继续等待下一次校准和传输；`--cli` 保留单次接收后退出的行为。

信息帧可能因截图不完整而损坏；未收到信息帧时须重新发送。系统显示颜色变化、HDR、模糊或非整数缩放会影响灰度解码，黑白模式可增加部分显示场景的稳定性，但不会保证避开任何水印干扰。遮挡窗口、鼠标和远程桌面压缩都可能造成帧丢失，可按缺失帧报告补发。

当前实现为单向屏幕通道，没有反向自动确认；发送端“完成”与接收端“完整”是不同状态。截图轮询速度取决于平台，默认间隔不构成吞吐量保证。
